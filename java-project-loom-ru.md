# Как Project Loom (виртуальные потоки) работает «под капотом»

Виртуальные потоки (JEP 444, финализированы в JDK 21; превью JEP 425/436 в 19/20) — это *не* потоки ОС и не «green threads» в классическом смысле времён Java 1.2. Это кооперативные пользовательские (user-mode) континуации, планируемые на реальные потоки ОС.

## 1. Три составные части

Каждый виртуальный поток состоит из:

1. **`java.lang.Thread`** — буквально тот же самый класс. Флаг помечает его как виртуальный (`Thread.isVirtual()`). Весь существующий код — `Runnable`, `ThreadLocal`, `UncaughtExceptionHandler` — работает без изменений.
2. **`jdk.internal.vm.Continuation`** — сам механизм приостановки: куче-размещаемый (heap-allocated) возобновляемый стек.
3. **Планировщик** — по умолчанию `ForkJoinPool` в режиме FIFO/async (`WorkQueue.asyncMode=true`), с параллелизмом = число ядер CPU и `maxPoolSize` по умолчанию 256. Настраивается через `jdk.virtualThreadScheduler.parallelism` / `.maxPoolSize`; можно заменить через `Thread.ofVirtual().scheduler(...)`.

Потоки ОС, исполняющие виртуальные потоки, называются **потоками-носителями (carrier threads)** — это просто рабочие (платформенные) потоки ForkJoinPool.

## 2. Континуации: ключевой механизм

`Continuation` владеет стеком виртуального потока, который хранится в куче в специальном объекте JVM — **`StackChunk`** (тип `oop` с особым битом в mark-word; сборщик мусора знает о нём нативно).

### Mount / Unmount / Yield

- **Mount (`Continuation.run()` / `enter()`)**: копирует кадры стека из `StackChunk` обратно на реальный машинный стек *потока-носителя* и переходит к точке приостановки. Исполнение продолжается так, будто ничего не случилось — локальные переменные, мониторы, адреса возврата все восстановлены.
- **Unmount (`Continuation.yield()`)**: обратный процесс. Это **интринзик** HotSpot (`_continuation_yield`). JVM выполняет *freeze* («заморозку»): обход стека от текущего кадра до входного кадра континуации с копированием содержимого каждого кадра (локальные переменные, стек выражений, мониторы, состояние интерпретатора / layout скомпилированного кадра, сохранённые регистры, указатель кадра, PC/BCI) в `StackChunk`.
- После freeze `yield()` *возвращается как обычный вызов* — но не в возобновлённый код; он возвращается к тому, кто вызвал `run()`, то есть в цикл планировщика. Планировщик затем просто запускает следующий виртуальный поток. Переключение контекста = один memcpy пары килобайт в кучу и обратно. Ни одного системного вызова, нулевое участие ядра.

### «Барьер возврата» (тонкость JIT-части)

Вот где всё становится непросто для скомпилированного (JIT) кода. Пусть C2-скомпилированный метод был заморожен посреди исполнения и позже «разморожен» (thaw) на *другом* носителе. Когда этот метод в итоге завершится, он **не должен** возвращаться в стек своего старого вызывающего — тот стек больше не содержит этот вызов (там могут находиться чужие кадры).

Решение: при заморозке скомпилированного кадра его адрес возврата пропатчен так, чтобы указывать на **стаб входа в континуацию (continuation-enter stub)**. При разморозке кадр возвращается с этим специальным адресом возврата, поэтому при обычном завершении метода управление попадает на стаб-барьер, который корректно завершает возврат континуации вместо «проваливания» в устаревший код вызывающего. Именно поэтому замороженные скомпилированные кадры хранятся вместе со своими метаданными, и именно поэтому в C2 есть dedicated-поддержка freeze/thaw (`freeze_entry`, пути thaw «from compiled», `StackChunkFrameStream`).

### Интерпретируемые и скомпилированные кадры

- **Интерпретируемые кадры** копируются через состояние интерпретатора (указатель на locals, список мониторов, BCP, вершина стека выражений).
- **Скомпилированные кадры** копируются вместе со spill-слотами регистров; при thaw скомпилированный кадр может потребовать **деоптимизации** (например, если класс был переопределён, пока поток был приостановлен) — в чанке хранится достаточно информации, чтобы восстановить состояние интерпретатора.
- Существуют быстрые пути: C2 пытается выполнить inline-freeze и «last-frame» thaw (один кадр → прямое копирование, минуя круговую поездку через чанк).

### GC и StackChunk

GC обрабатывает чанки лениво: кадры чанка сканируются как кадры стека (через `StackChunkFrameStream`), ссылки (oops) внутри обновляются, чанки со временем могут «relax-иться»/уплотняться. Поскольку стек живёт в куче, глубокие стеки просто выделяют более крупные чанки — стеки растут динамически (лимит по умолчанию ~1 МБ, задаётся через `Thread.Builder.stackSize`), а GC-нагрузка примерно пропорциональна суммарному размеру стеков приостановленных потоков — именно такова реальная модель стоимости Loom (тысячи потоков с неглубокими стеками = крошечный след в памяти).

## 3. Цикл планировщика

Поток-носитель по сути крутит такой цикл (`VirtualThread.runWorker`):

```
while (true) {
    vthread = queue.poll();          // очередь отправки FIFO ForkJoinPool
    vthread.continuation.enter();    // mount и исполнение до yield/завершения
    // когда enter() вернулся, vthread запаркован или завершён;
    // цикл продолжается — берём следующий
}
```

- `Thread.start()` **не** создаёт поток ОС — он просто отправляет континуацию виртуального потока в пул планировщика.
- `unpark()` вталкивает континуацию обратно в очередь исполнения (с корректной семантикой happens-before, как у `LockSupport`).
- Идентичность носителя намеренно скрыта: `Thread.currentThread()` внутри — всегда виртуальный поток.

## 4. Как «блокирующие» вызовы становятся неблокирующими

Главный трюк: **большинство блокирующих операций JDK были переписаны так, чтобы парковаться вместо блокировки носителя.**

- **Сетевой I/O**: `SocketChannel` и т.д. инструментированы подсистемой **poller**. Когда виртуальный поток упирается в блокирующее чтение из сокета, JVM вместо этого регистрирует дескриптор в небольшом наборе выделенных потоков-poller'ов (на базе `kqueue`/`epoll` через NIO-селекторы), поток паркуется (unmount), а когда fd готов — poller его «будит» (unpark). Покрыто всё: `ServerSocket.accept`, `Socket.getInputStream().read()`, TLS-хендшейки.
- **Таймеры**: `Thread.sleep`, `LockSupport.parkNanos`, таймауты идут через внутреннюю очередь таймеров планировщика — носитель освобождается немедленно.
- **Блокировки `java.util.concurrent`** уже использовали `LockSupport`, поэтому паркутся бесплатно.
- **`Object.wait()`** был пере реализован внутри на парковочную механику вместо блокировки носителя.
- **Компенсация**: если носитель *действительно* застрял (см. pinning, или блокирующий файловый I/O на файловой системе по умолчанию, который принципиально не может быть неблокирующим), планировщик временно добавляет потоки-носители (до `maxPoolSize`), чтобы не терять параллелизм CPU.

## 5. Pinning — исторический недостаток и его исправление

До JDK 24 виртуальный поток **пиновал** («прибивал») свой носитель (не мог отмонтироваться), когда:

- Он находился внутри `synchronized`-блока/метода — владение монитором было привязано к резидентной в стеке lock-записи кадра носителя, и перенос стека сломал бы блокировку.
- Он был заблокирован в **нативном (JNI) кадре** — нативный код держит сырые указатели в стек.
- `Object.wait()` — по тем же причинам.

**JEP 491 (JDK 24)** исправил мониторы: состояние блокировок, удерживаемых виртуальными потоками, теперь отслеживается в per-object списках мониторов, независимых от какого-либо стека, поэтому `synchronized` больше не пинует, а блокировка на мониторе корректно паркует/отмонтирует поток. Неустранимый остаточный pinning — нативные кадры (JNI critical regions и т.п.). Диагностика до JDK 24: `-Djdk.tracePinnedThreads=full`, плюс JFR-события `jdk.VirtualThreadPinned` и `jdk.VirtualThreadSubmitFailed`.

## 6. Интеграция с рантаймом

- **Стек-трейсы / `StackWalker`**: JVM может обойти *отмонтированный* поток, напрямую итерируя кадры `StackChunk` — без mount. Отладчики и JVMTI получили поддержку виртуальных потоков (события `ThreadStart/End`, `VirtualThreadMount/Unmount` в JFR).
- **ThreadLocals**: хранятся в map, на которую ссылается объект `Thread` в куче (им всё равно приходится жить в куче, поскольку стек перемещается между носителями). Отсюда и рекомендация Loom: «не пулируйте виртуальные потоки и не используйте thread-local кэши в больших масштабах».
- **Вложенные континуации** поддерживаются через `ContinuationScope` — yield раскручивает стек только до ближайшей подходящей области.
- **Новой модели памяти нет, вытесняющего планирования нет**: переключение происходит только в явных точках yield/park, поэтому цикл, нагружающий CPU, внутри виртуального потока монополизирует его носитель — CPU-bound работу всё равно следует выполнять на платформенных потоках.

## 7. Итог одним предложением

Виртуальный поток — это живущий в куче замораживаемый стек (`Continuation` + `StackChunk`); `yield()` копирует машинный стек в кучу и отдаёт поток ОС обратно в FIFO `ForkJoinPool`; все значимые «блокирующие» API JDK перепаяны на парковку (unmount) вместо блокировки, используя epoll/kqueue-poller'ы для сокетов и очереди таймеров для снов — и вот миллионы дешёвых потоков мультиплексируются на горстку потоков ядра с чисто пользовательскими переключениями контекста.
